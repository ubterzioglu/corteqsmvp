0. Yönetici Özeti

⚖️ Ana tablo: Cadde 3.0 çekirdek olarak tamamlanmış ve canlıda (feed + cafe + çarşı + tanıtım + bildirim + moderasyon + çoklu diaspora; Faz 0–9 ve kuyruk kapanışı, mig cadde300_001–014). Rebuild'den bu yana yeni cadde migration'ı yok (cadde300_015+ bulunmuyor) — yani açık kalemler "yarım bırakılmış kod" değil, bilinçli olarak ürün kararı veya ayrı faz bekleyen işler.

Açık işler iki kovaya düşüyor: (1) teknik borç/operasyon (B1 types regen, D-03 SMS sağlayıcı, legacy DROP, pg_cron zamanlama) ve (2) ürün yüzeyi/zenginleştirme (public profil vitrini, premium UI, ve ref'ten taşınabilecek cafe atmosferi / takip / kişi keşfi gibi fikirler). İkincisinin çoğu Bölüm C'deki sorular cevaplanmadan başlayamaz.
✅ Tamamlanmış (canlı, teyitli)

  • CKS band/skor feed sıralaması (SQL + TS ayna, testli)

  • Tanıtım kampanya backend'i + admin onay akışı + event ölçümü
  • Bildirim sistemi + zil + realtime; auto-moderasyon trigger'ları + kuyruk + ban
  • Çoklu diaspora (diaspora_key), cadde_settings ile ürün limitleri
  • Profil paneli parity (CaddeMyContentCard: Açık Cafelerim + Çarşı İlanlarım)
⛔ Açık / karar bekleyen (öne çıkanlar)
  • B1 types regen — cadde-internal.ts'te hâlâ db as any
  • D-03 SMS/OTP — altyapı kurulu, sağlayıcı + flag açık değil (stub)

B. ref/corteqs_plus ↔ Cadde 3.0 Karşılaştırması

Hikâye: Lovable üzerinde geliştirdiğimiz eski corteqs uygulamasını (corteqssocial-web/corteqs) referans olsun diye projenin yanına ref/ (eski adıyla reference/corteqs_plus) olarak klonladık. Oradaki Cadde, bizim Cadde 3.0'ın bir önceki nesli (Cadde 2.x). Altyapıda biz açık ara öndeyiz; deneyim/oyunlaştırma tarafında eski repo daha cömert.

Teknik gerçek: Eski kodu kopyala-yapıştır yapamayız. Eski Cadde, canlı DB'de artık yazmaya kapalı (write-revoked) ya da silinmiş tablolara yazıyor — kopyalanan kod derlenir, çalışır gibi görünür ama sessizce hata verir. Taşınacak her kalem fikir ve arayüz olarak alınıp bizim RPC-only sözleşmemize yeniden yazılır.

C. Soru İşaretleri & Karar Bekleyenler

Ortakla masaya yatırılacak kararlar. Yeşil satır = önerilen varsayılan. S1–S9 ürün/UX soruları; K1–K4 Bölüm A'dan doğan operasyon/iş-modeli kararları.

S1 — Takip grafiği geri gelsin mi?
Cadde 3.0, user_follows'u bilinçle emekliye ayırdı. Plus'taki takip + "sana benzeyen kişiler" geri isteniyorsa: yeni cadde_follows (diaspora_key'li) + follow_cadde_user_v1 RPC + CKS skoruna takip sinyali + gizlilik kuralı (kim kimi takip ediyor görünür mü?).
▸ Öneri: MVP'de takipsiz keşif/öneri ile başla; takip ayrı faz (Bölüm B, S5 ile birlikte değerlendir).
S2 — CafeAmbiance gerçek mi, oyuncak mı?
Post-it/anket/jukebox şu an localStorage'da: herkes yalnız kendi yazdığını görüyor. (a) Gerçek paylaşımlı → 2-3 yeni tablo + RPC + Realtime + moderasyon (post-it içeriği de taranmalı); (b) "kişisel ambiyans" lokal kalır (ucuz ama yanıltıcı); (c) hiç alınmaz.
▸ Öneri: önce (b) lokal sürümle yüzeyi yayınla, gerçek paylaşımlı (a) sürümü ayrı iterasyona bırak.
S3 — Cafe tür modeli + TR kısıtı çatışması
Plus: "TR (+90) yalnız relocation/expo'ya girer; TR cafe'lere yalnız TR-yerleşikler". Fin: can_join_cadde_cafe (limit/doğrulama odaklı, tür kavramı yok). Birleşecek mi? Birleşirse SQL+TS ayna sözleşmesi ve testleri birlikte güncellenmeli. Relocation/expo türleri ürün olarak isteniyor mu?
S4 — Köprü erişim bayraklarının gerçek kaynağı
Plus'ta Köprü erişimi localStorage ile açılıyor — fin'e böyle gelemez. Fin'de nereye yazılmalı: user_profile_attributes'a yeni AFS attribute (relocating_target_country, digital_community_optin) mü, yoksa user_verifications genişletmesi mi? (AFS attribute eklemek migration + rol kuralı ister.)
▸ Öneri: AFS attribute olarak çöz; can_post_kopru zaten attribute'lara bakıyor (ayna sözleşmesi korunur).
S5 — Dinamik like eşiği vs CKS
Plus'ın "akış hızına göre baraj"ı ile CKS aynı problemi farklı çözüyor. CKS'ye "yoğunluk barajı" parametresi olarak eklensin mi (cadde_settings.feed.flow_threshold_enabled gibi), yoksa görmezden mi gelinsin?
S6 — Çarşı görsel yükleme & bucket
Hangi bucket (yeni cadde-media?), boyut/format limiti, ilan başına kaç görsel, görsel de moderasyona girecek mi (Bölüm A "görsel auto-moderasyon" açık)? create_carsi_item_v1 imza değişikliği migration ister.
S7 — Kişi arama gizlilik sınırı
Arama hangi alanlarda yapılır? user_profile_attributes.visibility yalnız public/private — private alanlar öneri skorlamasına bile girmemeli mi? (Plus'ta bu ayrım hiç yok.)
▸ Öneri: yalnız public alanlar; private hiç skorlanmaz.
S8 — Öncelik sırası
Önerilen kesim: önce public profil yüzeyi + Çarşı görseli + dünya saatleri/ticker (düşük risk, açık kuyruğu kapatır), sonra S1–S3 kararları → cafe deneyimi → sosyal grafik. Onaylanıyor mu, sıra değişsin mi?
S9 — ref/corteqs_plus canlı bir ürün mü?
Plus repo'su aktif geliştiriliyorsa iki yönlü senkron beklentisi var mı, yoksa tek seferlik fikir kaynağı mı? Tek seferlikse bu doküman yeterli; sürekli senkron isteniyorsa süreç + aktarım öncesi git -C ref pull tanımlanmalı.
K1 — SMS/OTP sağlayıcı kararı (D-03)
Telefon doğrulama altyapısı kurulu, flag kapalı. Sağlayıcı: Twilio / Vonage / Supabase phone provider / e-posta-fallback'li demo? Maliyet + KVKK ürün sorumlusunda. Seçilince OTP Edge Function + flag true.
K2 — Legacy 5 tablo DROP zamanlaması
Write-revoked tablolar ne zaman DROP edilecek? Canary gözlemi tamamlandı mı? user_follows'taki 1 satır (R-06) drop kararına dahil. Karar dokümanı + migration gerekiyor.
K3 — Premium iş modeli (D-07)
Kademeli üyelik (Çarşı ilan limiti vb.) bu fazda yüzeylenecek mi? Feature-bazlı entitlement (afs_features) ile mi, yoksa gerçek abonelik (Stripe/Paddle) ayrı proje olarak mı? Cadde 3.0 kapsamı bugün entitlement UI içermiyor.
K4 — B1 types regen + pg_cron operasyonu
Geçerli SUPABASE_ACCESS_TOKEN sağlanıp types regen edilecek (yeni RPC'ler tip-güvenli olsun)? Ayrıca canlıda pg_cron var mı — yoksa cafe.expiring bildirimi için dış cron/Edge Function alternatifi kararı.
